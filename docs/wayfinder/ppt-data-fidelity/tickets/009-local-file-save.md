## Question

如何完成总路线图的 File System Access 双路径保存，让用户选择本机文件后继续原地保存，而不把浏览器权限
或文件句柄带进发布包，也不在磁盘失败时丢掉未保存状态？

| 行为 | 约束与验收 |
|---|---|
| 保存到文件 / 更换保存位置 | 能力检测，不使用 UA；选择器在真实用户激活内调用，默认只接受 `.pptx`；成功关闭写入流后才记住目标 |
| 保存副本与不支持 FSA 的浏览器 | 显式下载入口始终可用；无 FSA 的 Ctrl/Cmd+S 回退下载，拒绝或取消选择不偷偷下载 |
| Ctrl/Cmd+S 与 Shift 另存为 | 复用同一文件任务锁；重复触发不能弹多个选择器或绕过文稿加载/只读/转换限制 |
| 文件持久化与未保存状态 | 字节生成不是落盘；write/close 失败中止写入，保留原文件和 dirty；成功后才确认保存点 |
| 异步与会话隔离 | 生成期间文稿变更则拒绝交付混合版本；写入期间的新编辑仍为未保存；切换/新建/冷恢复不继承旧句柄 |
| 产品反馈 | 完整中英文、目标文件名原文、等待/取消/拒绝/错误/成功；320px 与真实键鼠操作；下载与保存字节可重新打开 |
| 交付门禁 | 原性能/体积预算不变，四项门禁及根/子路径完整生产回归通过；确定性固件复用现有编辑与旧格式样本 |

沿用已确认的公开 DOM、原生输入、浏览器文件/存储边界。自动化选择器返回真实浏览器文件句柄，读回持久化文件
并通过产品文件输入重开；故障在选择器或文件流边界制造，不替换编辑器、序列化或恢复控制器。

规范依据：[选择器用户激活与写入关闭](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access)、
[文件系统权限](https://wicg.github.io/file-system-access/)。句柄仅存当前会话内存，不跨刷新持久化，也不自动写回
通过普通文件输入打开的来源；必须由用户明确选择保存目标。Windows PowerPoint 真机仍是独立验收项。

## Answer（2026-09-06）

产品层双路径已完成，使用方式与验证边界见[本机文件保存](../../../local-file-save.md)。浏览器选择器、权限和
会话句柄均留在官网；共享编辑核心仅提供不确认交付的序列化与一次性保存点确认。

| 完成项 | 最终证据 |
|---|---|
| 本机保存、另存为、显式下载与快捷键 | 实际 OPFS 文件流读回重开；拒绝/取消不下载，新目标失败保留旧目标 |
| 延迟保存点 | 写入期间继续编辑、撤销回旧保存点、重做到交付版本；恢复 v1 空元数据事务兼容、一次性确认及历史合并屏障 |
| 生成与交付失败 | 网络暂停实际序列化模块后原生编辑；create/write/close 失败与部分写入中止；原文件不变且可重试 |
| 产品与会话边界 | 中英文与原始目标名、原生 Tab/Enter、320px 触点；旧格式转换、新建文稿与真实冷恢复后重新授权 |
| 完整门禁 | 四项全仓门禁 + 根路径和 `/web-ppt/` 不带专项过滤的完整生产 Chrome 回归全部通过 |

最终实测 5,906 项断言、186 个快照、550 对独立进程 SVG 指纹；editor 主入口 282,156B / 69,731B gzip，
edit-core 默认入口 82,494B gzip。删除/撤销/重做 p95 为 4.7 / 6.7 / 5.6ms，原性能和体积上限均未调整。
Standards / Spec 独立复审均无未解决发现。

不把 OPFS 文件句柄测试冒充系统原生选择器自动化或 PowerPoint 真机证据；恢复仍基于原始输入 fingerprint，
不宣称覆盖后的新文件字节会自动匹配旧恢复日志。后续集成验收继续跟踪这些已公开边界。
