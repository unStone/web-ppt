## Question

`0.5.0-beta.2` 已在 `@next` 上（八包同版本）。把编辑线转正到 `latest` 前，还欠哪些证据与动作，
顺序是什么？

| # | 动作 | 说明 |
|---|---|---|
| 1 | PowerPoint 真机验收 | [票据 010](010-prove-m1-save.md) 的 Windows 自托管工作流跑出 30/30 成功报告——编辑产物「真实软件兼容」的最后一块证据，缺它不转正 |
| 2 | beta 反馈窗口 | 至少一个可用性反馈周期；期间修复走 `0.5.0-beta.N` |
| 3 | 数字校准 | README / 官网全部体积、断言、性能数字按发布当日实测（AGENTS 约定），中英 README 同步 |
| 4 | CHANGELOG 转正 | beta 条目合并成 `0.5.0` 正式条目，破坏性变更核对 |
| 5 | 安装指引切换 | README 「`@next` 混装警告」段落改为稳定安装；站点 editor 页说明同步 |
| 6 | 版本与 tag | 八包 bump `0.5.0` → `git tag v0.5.0` → Trusted Publishing 流水线（顺序 core → edit-core → viewer-core → editor → react → vue → fonts → collab） |
| 7 | dist-tag 收尾 | 确认 `latest` 指向 0.5.0；`next` 后续留给 0.6 线 |

验收：上述七项全部留痕（run ID / commit / npm view 输出）；`npm view` 各包 `latest` 与 readme 正确
（防 README.zh-CN 陷阱复发）；全部门禁绿。

## Answer

2026-10-29 用户决定：Windows 真机验收（步骤 1）与 beta 反馈窗口（步骤 2）延后，0.5.0 先行转正；后续稳定版仍以真机结果为准（roadmap §7.3 已同步）。步骤 3–7 当日执行。

## Resolution

| # | 步骤 | 证据 |
|---|---|---|
| 3 | 数字校准 | 发布当日跑四项门禁实测；官网 JSON-LD `softwareVersion` 同步 0.5.0，README 体积/断言数与 dist 一致（verify 通过） |
| 4 | CHANGELOG 转正 | `## 0.5.0 - 2026-10-29` 条目：beta.7 全部内容转正、破坏性变更核对（无 API 撤除，仅矩阵 API 沿渲染链求值的语义变化）、安装与 Windows 豁免说明 |
| 5 | 安装指引切换 | 中英 README 与 `docs/api/editor.md` 改为无版本号稳定安装；`@next` 标注留给 0.6 线 |
| 6 | 版本与 tag | 八包 bump `0.5.0` → tag `v0.5.0` → `release.yml` Trusted Publishing 按序发布 |
| 7 | dist-tag 收尾 | `npm view` 八包 `latest → 0.5.0`，`next` 保持 `0.5.0-beta.7` 留给 0.6 线 |

流水线 run ID 与 npm view 输出见 tag `v0.5.0` 的 release 运行记录。Windows 真机验收仍开放在 [010](010-prove-m1-save.md)。
